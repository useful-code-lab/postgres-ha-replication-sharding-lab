# 🐘 PostgreSQL: от репликации до отказоустойчивого и распределённого кластера

Практическая лаборатория, которая показывает, **как шаг за шагом превратить обычный PostgreSQL-сервер в отказоустойчивую и распределённую систему**.

Проект можно использовать как учебный стенд, шпаргалку для настройки PostgreSQL-инфраструктуры или основу для собственных экспериментов с репликацией, HA и шардированием.

Все сценарии воспроизводятся локально в виртуальных машинах **Multipass**, поэтому для экспериментов не нужен отдельный серверный кластер.

---

## 🎯 Что вы получите от проекта

Изучая этот репозиторий, вы сможете не просто прочитать о технологиях PostgreSQL, а **самостоятельно собрать и проверить каждый сценарий**.

Проект помогает разобраться:

* как создать резервную копию PostgreSQL через физическую репликацию;
* как синхронизировать данные между PostgreSQL-серверами;
* чем отличаются синхронная и асинхронная репликации;
* как организовать автоматический `failover` при отказе основного сервера;
* как Patroni определяет текущего лидера кластера;
* зачем в HA-кластере нужен etcd;
* как HAProxy направляет подключения к актуальному серверу;
* чем физическая репликация отличается от логической;
* как передавать только необходимые таблицы через `PUBLICATION` / `SUBSCRIPTION`;
* как подготовить PostgreSQL к горизонтальному масштабированию;
* как Citus распределяет данные между несколькими узлами;
* что такое `shard pruning` и как PostgreSQL определяет нужный воркер;
* как самостоятельно проверить состояние репликации, HA-кластера и распределённых запросов.

Главная ценность проекта — **каждый этап можно запустить, сломать, проверить и восстановить самостоятельно**.

# 1. Streaming Replication

📁 [`stage-1-streaming-replication`](stage-1-streaming-replication)

### Что изучается

На первом этапе создаётся связка:

```text
Primary PostgreSQL
       │
       │ WAL
       ▼
Replica PostgreSQL
```

Используется стандартный механизм **PostgreSQL Streaming Replication**.

### Что можно получить на практике

После прохождения этого этапа вы будете понимать:

* как PostgreSQL передаёт изменения через WAL;
* как создаётся физическая реплика;
* как работает `pg_basebackup`;
* зачем нужен `wal_level = replica`;
* чем отличается синхронная репликация от асинхронной;
* как проверить, что реплика действительно получает изменения;
* что происходит с данными при остановке Primary.

### Что можно повторить

Создать реплику:

```bash
pg_basebackup -R ...
```

Затем проверить состояние репликации и убедиться, что изменения с Primary появляются на Replica.

### Когда эти знания полезны

Этот этап является фундаментом для понимания более сложных PostgreSQL-кластеров.

Без понимания физической репликации сложнее разобраться в Patroni, failover и других HA-сценариях.

---

# 2. High Availability с Patroni

📁 [`stage-2-ha-patroni`](stage-2-ha-patroni)

На втором этапе репликация превращается в **отказоустойчивый PostgreSQL-кластер**.

Используются:

* PostgreSQL;
* Patroni;
* etcd;
* HAProxy.

Архитектура:

```text
             ┌──────────────┐
             │     etcd     │
             │ Cluster State│
             └──────┬───────┘
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
    ┌───────────┐       ┌───────────┐
    │ PostgreSQL│       │ PostgreSQL│
    │  Primary  │──────▶│  Replica  │
    └─────┬─────┘       └───────────┘
          │
          ▼
      ┌─────────┐
      │ HAProxy │
      └─────────┘
```

### Что вы сможете понять

* зачем нужен автоматический `failover`;
* как определяется текущий лидер;
* как Patroni управляет PostgreSQL;
* какую роль играет etcd;
* как приложение может подключаться к кластеру через HAProxy;
* что происходит при отказе Primary;
* как выполняется обратное переключение.

### Проверка отказоустойчивости

Например, можно остановить основной сервер:

```bash
multipass stop pg-master
```

После этого проверить состояние кластера:

```bash
sudo patronictl -c /etc/patroni.yml list
```

Цель эксперимента — увидеть, как Replica становится новым лидером.

# 3. Logical Replication

📁 [`stage-3-logical-pub-sub`](stage-3-logical-pub-sub)

На третьем этапе рассматривается другой подход к репликации — **логическая репликация PostgreSQL**.

Вместо копирования всей физической структуры базы можно выбрать, **какие данные необходимо передавать**.

Используется модель:

```text
Publisher
    │
    │ PUBLICATION
    ▼
 PostgreSQL
    │
    │ SUBSCRIPTION
    ▼
Subscriber
```

### Что вы получите

После прохождения этапа станет понятнее:

* чем logical replication отличается от streaming replication;
* как работает `PUBLICATION`;
* как работает `SUBSCRIPTION`;
* как реплицировать отдельные таблицы;
* где логическая репликация может быть удобнее физической;
* почему Subscriber может использоваться иначе, чем физическая Replica.

### Практический сценарий

Можно выбрать конкретную таблицу и настроить её передачу между PostgreSQL-серверами.

Это позволяет экспериментировать с архитектурами, где **не требуется копировать всю базу целиком**.

# 4. Шардирование PostgreSQL с Citus

📁 [`stage-4-sharding-citus`](stage-4-sharding-citus)

Последний этап посвящён уже не отказоустойчивости, а **горизонтальному масштабированию данных**.

Используется **Citus**.

Вместо одной большой таблицы:

```text
              orders
                 │
                 ▼
        ┌────────────────┐
        │ Один PostgreSQL│
        └────────────────┘
```

данные распределяются между несколькими worker-узлами:

```text
                 Coordinator
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Worker 1    Worker 2    Worker 3
       Shards       Shards      Shards
```

### Что можно изучить

* что такое distributed table;
* как таблица распределяется между worker-узлами;
* как Citus хранит информацию о shard'ах;
* что такое `shard pruning`;
* как координатор определяет нужный worker;
* как анализировать план распределённого запроса.

### Проверка размещения shard'ов

Например:

```sql
SELECT
    shardid,
    nodename,
    shardminvalue,
    shardmaxvalue
FROM pg_dist_shard s
JOIN pg_dist_placement p ON s.shardid = p.shardid
JOIN pg_dist_node n ON p.groupid = n.groupid
WHERE s.logicalrelid = 'orders'::regclass;
```

Так можно увидеть, **на каких узлах находятся части таблицы**.

### Проверка распределённого запроса

```sql
EXPLAIN (VERBOSE)
SELECT *
FROM orders
WHERE id = 42;
```

В плане можно увидеть:

```text
Custom Scan (Citus Adaptive)
```

Это позволяет на практике исследовать, как Citus определяет узел, на котором необходимо выполнить запрос.

# 🧪 Почему проект удобно использовать как лабораторию

Проект специально разбит на независимые этапы.

Можно начать только с первого:

```text
Stage 1 → Replication
```

а затем постепенно двигаться дальше:

```text
Stage 1
   ↓
Stage 2 → High Availability
   ↓
Stage 3 → Logical Replication
   ↓
Stage 4 → Sharding
```

Это позволяет изучать технологии **не одновременно, а последовательно**, понимая, какую задачу решает каждый следующий уровень.
